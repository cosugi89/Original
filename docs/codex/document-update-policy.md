# 仕様書 / TODO 更新方針

この文書は、仕様書、全体 TODO、作業メモをどのタイミングで、どこまで更新するかを定める。
`AGENTS.md` から参照される、文書運用の詳細ルールとして扱う。

## 1. 基本原則

- 文書は「あとでまとめて直す」前提にせず、作業の節目ごとに同期する。
- 仕様と実装が衝突した場合は、原則として現行実装を正として仕様書を更新する。
- TODO は backlog として機能する状態を保ち、完了済み、重複、短命なメモを溜めない。
- 一時的な調査メモやタスク分解は恒久資料と分離し、消化後は削除または要点だけを恒久ドキュメントへ戻す。
- 文書本文は日本語で書く。これは `docs/` 配下だけでなく、`.codex/` 配下のエージェント向け方針、現状メモ、作業メモにも適用する。コード識別子、API 名、ファイルパス、Unity メニュー名などは可読性を優先して原文表記のままでよい。

## 2. 文書の役割分担

### 2.1 `docs/specs/*.md`

- 恒久的な仕様、設計、データ構造、画面構成の正本。
- ユーザーと合意済みの方針、または現行実装で確定した挙動を書く。
- 未確定事項を大量に混ぜず、必要なら「未確定」と明示する。

### 2.2 `docs/todos/プロジェクト全体TODO.md`

- プロジェクト横断の未完了タスク一覧。
- 今後も残る実装課題、接続課題、仕様確定待ちを残す。
- 仕様化前のゲーム改善アイデアは、通常の実装 TODO と混ぜず、専用の「ゲーム改善アイデア TODO」セクションに置く。
- 完了済みは `[x]` 化するか、まとまりとして役目を終えたら削除して整理する。
- 同じ内容を別セクションや別メモに重複させない。

### 2.3 `docs/codex-notes/*.md` または短期作業用 TODO

- スレッド内で一時的に使う作業メモ、調査メモ、分解タスク置き場。
- Findings、段階分け、洗い出し結果など、短期で燃やし切るものを置く。
- 残タスク消化後は削除するか、必要部分だけを仕様書 / 全体 TODO に移す。

## 3. 更新トリガー

次のいずれかに当てはまる場合は、関連文書の更新要否を必ず確認する。

- 実装によって挙動、責務、データ構造、UI 構成、シーン構成が変わった
- ユーザーとの会話で仕様、方針、命名、スコープが確定した
- TODO の状態が変わった。未着手が着手済みになった、完了した、粒度を切り直した
- 調査の結果、新しい改善点や未解決事項を追跡する必要が出た
- 大きなリファクタや段階実装で、節目ごとに現在地を残す必要がある

## 4. 更新タイミング

### 4.1 作業開始時

- 対象機能に関係する仕様書と TODO を読む。
- 既存文書に記載済みの前提を把握してから作業に入る。

### 4.2 作業中

- 長いリファクタや多段階実装では、節目ごとに文書同期を行う。
- その場しのぎのメモが必要な場合だけ、一時メモや短期 TODO を追加する。

### 4.3 作業完了前

- 変更内容が仕様書に反映されているか確認する。
- 全体 TODO の完了 / 未完了 / 優先度が現在地に合っているか確認する。
- 一時メモが不要になったら削除する。

## 5. 書き分けルール

### 5.1 仕様書へ書くもの

- 実際のシステム挙動
- 採用済みの設計方針
- データ構造や UI 構成の確定内容
- 現行実装を前提にした制約や前提条件

### 5.2 全体 TODO へ書くもの

- まだ終わっていない作業
- 今後着手する必要がある接続や演出や画面
- 仕様未確定のため保留している実装課題
- 次の作業順に影響する残課題
- 仕様化前だが継続的に検討したいゲーム改善アイデア。ただし、採用方針が固まったら該当する実装 TODO や仕様書へ移す

### 5.3 一時メモへ書くもの

- そのスレッドだけで使う分解タスク
- 調査中の Findings
- 実装前の洗い出し
- 消化後に残す必要がない補助メモ

## 6. 定期更新の定義

このプロジェクトでは「定期的に更新する」を、時間ベースではなく作業ベースで定義する。

- 対象機能に変更が入ったターンでは、同じターン内で文書同期の要否を確認する
- 大きな実装は、完了時だけでなく段階完了ごとに同期する
- 会話中に仕様確定が起きた場合は、その決定が失われる前に文書へ反映する

必要なら別途、週次や日次で文書棚卸しを行う自動化を追加してよいが、この文書だけでも最低限の同期が回る状態を目標とする。

## 7. 更新時の実務ルール

- `最終更新` のような日付欄がある文書は、更新時に実日付へ合わせる
- 重複記述は増やさず、既存セクションを直して正本を保つ
- 将来案を書くときは、現行仕様と混ざらないように区別する
- TODO は「行動可能な粒度」で書き、抽象論だけを残さない
- 仕様未確定事項は、確定事項のように書かない

## 8. 迷ったときの判断順

1. これは確定済みの仕様 / 現行挙動か
2. これは未完了タスクか
3. これは今だけ必要なメモか

判断結果に応じて、次へ振り分ける。

- 1 なら `docs/specs/*.md`
- 2 なら `docs/todos/プロジェクト全体TODO.md`
- 3 なら `docs/codex-notes/*.md` または短期 TODO
