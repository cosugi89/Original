# エージェント実装方針

このメモは、このワークスペースでの Codex の作業方針です。
プロジェクト仕様ではなく、AI が実装判断をするときの基準として扱います。

## 優先順位

- 可能な限り、クラス数とファイル数を増やしすぎない。
- 教科書的な分割よりも、読む疲労が少ない構成を優先する。
- 抽出したメソッドが一度しか使われない場合は、関連ロジックを呼び出し元に残すことを優先する。
- private メソッドへの抽出は、役割が明確に違う、境界に意味がある、または再利用の可能性が高い場合に限る。
- ユーザーの発話が質問である場合は、まず質問へ回答し、明示的に依頼されていない限り実装、編集、生成へ進まない。
- ユーザーからの最新の直接指示は、このメモより優先する。
- このファイルを含む `.codex/` 配下の文書も日本語で記述する。コード識別子、API 名、ファイルパス、Unity メニュー名などは必要に応じて英語のまま残してよい。

## リファクタリング傾向

- 抽象的なきれいさのためだけに、小さな controller、presenter、executor、helper クラスへ細分化しない。
- ファイルを行き来しないと読めない薄いクラス群より、流れが読める一つのまとまったクラスを優先する。
- 一連の処理として読めるロジックは、一度しか使わない private メソッド群へ分割するより、少し長めのメソッドとして残すことを許容する。
- ファイル分割は、その分離が長く保てて、理由を簡単に説明できる場合だけ行う。
- 定数や enum が本当に共有基盤である場合は、似た定義を複数箇所に置かず、共通定義を一つ用意して呼び出し側から再利用する。
- 共有 enum や定数は管理コストを低く保つ。専用の共通置き場にまとめ、呼び出し側から再利用することを優先する。

## 命名方針

- 型名は「対象 + 役割」の順にし、末尾で責務が分かる名前を選ぶ。曖昧な `Service` は新規コードで使わない。
- `Manager` は、ゲーム内の状態を正本として保持・更新する窓口に使う。例: `InventoryManager`、`AppearanceManager`、`ProgressManager`。
- `Store` は、永続データの読み書きをまとめる窓口に使う。保存形式や媒体を表す具体実装は `JsonFile` のように末尾へ置く。例: `UserDataJsonStore`、`UserDataJsonFile`。
- シーンやダイアログをまたぐ入力と結果は `Request` / `Result` とする。入口で必要な準備を行う型は `Initializer` とする。
- Dialog を制御する `MonoBehaviour` は `対象名 + Dialog` の型名に統一する。対応する入力と結果は `対象名 + DialogRequest`、`対象名 + DialogResult` とし、`Dialog + 対象名` や `Response` を混在させない。
- 異なる表現・層の変換は `Adapter`、Unity 上の見た目部品を直接制御する `MonoBehaviour` は `Controller` とする。これらは状態の正本を持たない。
- 変数名・プロパティ名も型の責務に合わせる。たとえば保存窓口は `userDataStore`、見た目の正本は `appearanceManager`、シーン遷移入力は `battleSceneRequest` のように、旧名称を引き継がない。

## アクセス修飾子

- 新規に作る型やAPIでは `internal` を使わない。外部から呼び出す型、enum、メソッドは `public`、実装詳細は `private` とする。

## UIViewController の公開API

- 新規の UIViewController は、表示状態を切り替えるためだけの enum や内部状態を原則 private にする。
- 呼び出し側には `SetState(state, ...)` のような表示実装に依存するAPIではなく、`ShowSkill(icon)`、`ShowEmpty()`、`ShowLocked(reason)` のように、表示したい意図を表すメソッドを公開する。
- 状態別の公開メソッドが共通の切替処理を持つ場合は、`private SetState(...)` に集約する。`SetState` は UIViewController 内部の実装詳細として扱い、public にはしない。
- 複数の画面や機能で共有するゲーム上の判断を呼び出し側に委ねる必要がある場合だけ、共有 enum や表示モデルを public にしてよい。単一 UIViewController 内の見た目切り替えはその理由にならない。
- optional 引数を組み合わせて無意味な呼び出しを許すAPIは避ける。状態ごとに必要な値が違う場合は、用途別の公開メソッドへ分ける。
- UIViewController は表示の正本を持たず、受け取った値を描画する。ゲーム状態の判断や保存は Manager など呼び出し側の責務に置く。

## Prefab UI の責務

- 再利用する Prefab の MonoBehaviour は、Prefab 内の画像、テキスト、表示状態、配色を一箇所で管理する。
- Screen 固有の View は、ゲームデータをPrefab用の表示意図へ変換し、クリックなど画面固有の入力を扱う中間アダプタとして保つ。
- 見た目が同じでもクリック後の意味が異なるViewを、抽象化だけを理由に一つのクラスへ統合しない。
- Prefab の公開APIは `Init`、`Setup`、意図を表すランタイム更新メソッドを優先し、呼び出し側が個々の GameObject を直接切り替えないようにする。

## 分割してよい理由

- 新しい型が複数の機能やシーンから再利用される。
- 新しい型が永続データやマスターデータの明確な正本になる。
- Unity の serialization、Inspector 配線、ライフサイクル処理が専用コンポーネントによって明らかに扱いやすくなる。
- pure logic が抽出によって意味のある単位でテストしやすくなり、Unity 依存から切り離せる。
- 一つのクラスが明らかに異なる責務を混ぜており、分離によって移動コスト以上に混乱が減る。

## BattleScene 固有の指針

- 分離する価値が明確でない限り、`BattleScene` を主要な orchestration class として保つ。
- scene 内だけで使う flow は、一度しか使わない helper クラスを作るより `BattleScene` 内へ集約する。
- 実行時の正本データは、必要に応じて `UserData`、`StageData`、既存 service に置く。
- `BattleScene` からしか触らない presentation detail のために新規ファイルを増やすことは避ける。ただし、既に境界が確立され、繰り返し使う価値がある場合は例外とする。
- 新しいクラスを追加したり一度しか使わないメソッドを抽出したりする前に、将来そのコードを読む人の負担が本当に減るかを確認する。

## リファクタリング前の実務チェック

次の順番で確認する。

1. 現在のクラスに残しても処理の流れが分かりにくくならないか。
2. 抽出した場合、読む負担の減少がファイル移動コストを上回るか。
3. 抽出先は再利用されるか、または本当に別責務を表しているか。
4. そうでないなら、現在の場所に残してファイル追加を避ける。
